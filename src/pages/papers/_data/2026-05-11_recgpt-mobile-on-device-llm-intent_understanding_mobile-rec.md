## 1. 摘要与核心贡献

### 研究问题

在现代电商系统中，从用户最近交互行为预测其下一个搜索查询是一个关键问题，尤其在用户意图快速演变的场景下更具挑战性。传统的云端推荐系统虽然能有效利用用户行为数据，但存在以下问题：首先，移动端对低延迟实时推理有严格要求，集中式架构在边缘设备和远程服务器之间引入了不可避免的通信延迟；其次，云端部署导致推理成本高昂，难以快速感知用户意图的快速变化。

RecGPT-Mobile 论文正是针对这一痛点，提出在移动设备上直接部署轻量级 LLM 作为意图理解代理，通过本地实时处理用户行为数据来捕捉用户兴趣的演变，并实时调整推荐结果。

### 方法概要

论文提出了 RecGPT-Mobile 框架，其核心设计包括：

1. **用户行为收集模块**：作为本地仓库收集和缓存用户行为数据
2. **Prompt 构建模块**：将原始行为和画像数据合成为结构化 Prompt
3. **意图代理（Intent Agent）**：将复杂的用户行为信号转化为清晰的用户意图查询
4. **物品检索模块**：基于生成的意图查询执行搜索
5. **LLM 训练模块**：采用监督微调、Prompt 适配和推理优化

关键创新在于设计了**意图漂移检测机制**，通过熵变化、Jaccard 相似度和 Jensen-Shannon 散度三个维度融合评估用户意图变化，只有当漂移程度超过阈值时才触发 LLM 推理，从而在保证推荐准确性的同时控制移动端计算资源消耗。

### 主要结果

论文在淘宝移动端进行了大规模在线 A/B 测试，覆盖数百万真实用户和多种购物场景，历时一个月。结果显示 RecGPT-Mobile 在四个 feed 场景下均取得了显著提升：

- **CLICK（点击率）**：平均提升 +1.8%
- **PAY（支付转化）**：平均提升 +2.7%
- **GMV（成交总额）**：平均提升 +2.5%

### 核心贡献

论文声称的贡献点如下：

1. **首个移动端 LLM 推荐系统实现**：本文首次在移动设备上实现了基于 LLM 的推荐系统，采用基于偏好的优化和轻量级模型压缩技术，使基于 LLM 的检索系统能够在移动端高效部署。

2. **意图代理设计**：设计了将隐式用户行为转化为显式意图查询的意图代理，以及频率控制机制，用于减少客户端的冗余推理并提高资源利用率。

3. **大规模实验验证**：在淘宝移动端进行了涉及数百万真实用户和多种购物会话的广泛实验，结果表明 RecGPT-Mobile 显著提升了推荐的相关性和可解释性。

## 2. 业界进展与相关工作

### 领域发展脉络

用户意图理解和推荐系统的发展经历了几个重要阶段。早期基于协同过滤的方法主要依赖用户-物品交互矩阵的统计信息，通过相似用户或相似物品来预测用户偏好。这类方法简单有效，但难以捕捉用户的细粒度意图和复杂的上下文信息。

随后，深度学习驱动的推荐系统（如 YouTube Deep Neural Networks、DeepFM、DIN 等）通过引入深度神经网络来学习用户和物品的高维表示，显著提升了推荐效果。这些方法虽然在语义理解上有所进步，但仍然依赖于显式的特征工程，难以处理用户意图的隐式表达。

近年来，大语言模型（LLM）的崛起为推荐系统带来了新的机遇。LLM 具有强大的语义推理能力，能够理解用户的隐式行为背后的真实意图。HSTU、OneRec、RecGPT 等工作尝试将 LLM 应用于推荐系统的各个环节，从训练数据构建到端到端生成式推荐。然而，这些方案都部署在云端服务器上，存在高推理成本和通信延迟的问题。

### 主要技术路线对比

当前该领域存在三条主流技术路线：

**路线一：云端 LLM 增强推荐**
代表工作包括 HSTU、OneRec、RecGPT 等。这类方法将 LLM 部署在云端，利用云端强大的计算资源进行推理。优点是模型规模不受限制，可以充分发挥 LLM 的能力；缺点是存在网络延迟和隐私风险，且推理成本高昂。

**路线二：端云协同推荐**
代表工作包括 EdgeRec、DIR 等。这类方法尝试将部分计算下沉到边缘设备，减少与云端的数据传输。优点是降低了延迟，提高了实时性；缺点是边缘设备的模型能力有限，通常只能部署轻量级模型。

**路线三：纯端侧推荐**
代表工作包括 Gong et al. 在 Kuaishou 的实践、MNN-LLM 等。这类方法尝试完全在移动端完成推荐推理，通过模型压缩技术（如量化、剪枝、知识蒸馏）将大模型部署到移动设备。优点是延迟最低、隐私最好；缺点是模型能力受限，需要精心设计才能达到可接受的效果。

### 最相关的前序工作

**EdgeRec（Gong et al., CIKM 2020）**
这是首个在移动淘宝上实现直接在设备上进行排序模型的研究工作，旨在降低信号延迟。EdgeRec 的核心思想是在客户端收集即时反馈，并将其用于后续的推荐调整。本文在其基础上更进一步，不仅在端侧进行排序，还部署了 LLM 来理解用户意图。

**DIR（Xi et al., KDD 2023）**
DIR 直接在移动设备上集成重排序框架，解决云端重排序的延迟处理问题。该工作证明了端侧部署复杂模型的可行性。本文借鉴了 DIR 的端侧部署经验，但将重排序模型替换为更强大的 LLM 意图代理。

**RecGPT（Yi et al., arXiv 2025）**
这是论文团队之前的工作，提出了基于 LLM 的生产级推荐框架，将日志拟合方法替换为以意图为中心的推理。RecGPT 将用户兴趣挖掘、物品标注、检索和解释生成整合到一个闭环中。本文可以看作是 RecGPT 的移动端轻量化版本。

**OneRec（Deng et al., arXiv 2025）**
OneRec 是一个统一的端到端生成式推荐框架，取代了传统的级联策略。该工作展示了 LLM 在统一推荐框架中的潜力。本文采用类似的思想，但针对移动端的资源约束进行了专门优化。

### 本文定位

RecGPT-Mobile 在上述技术路线中处于一个独特的位置：它是首个将 LLM 完整能力（而不仅仅是压缩版小模型）部署到移动端进行用户意图理解的工业级实践。论文的核心贡献不是提出新的模型架构，而是解决了 LLM 移动端部署的一系列工程挑战，包括：如何在严格的资源约束下保持模型效果、如何设计有效的意图漂移检测机制来控制推理频率、以及如何在真实电商环境中验证方案的有效性。

## 3. 详细技术方案

### 3.1 整体框架

RecGPT-Mobile 的整体架构包含五个核心模块，形成一个完整的端到端意图理解和推荐流程：

```
用户行为序列 B → 用户行为收集模块 → Prompt 构建模块 → Intent Agent → 物品检索模块 → 推荐结果
                    ↑                                                        ↓
                 LLM 训练模块 ←←←←←←←←←←←←←←←←←←←←←←←←←←←←← (反馈循环)
```

**模块间协作流程**：
1. 用户行为收集模块实时捕获用户在移动端的各种交互行为（点击、加购、收藏、购买等）
2. 当用户触发高意图行为时，Prompt 构建模块被激活，将原始行为和画像数据合成为结构化 Prompt
3. Intent Agent 处理合成的 Prompt，将复杂的行为信号转化为清晰的用户意图查询
4. 物品检索模块基于生成的意图查询执行搜索，返回一组候选物品
5. LLM 训练模块持续学习用户反馈，通过 SFT、Prompt 适配和推理优化保持模型的适应性和准确性

### 3.2 关键模块详解

#### 3.2.1 用户行为收集模块

该模块作为本地仓库，收集和缓存用户在移动端的行为数据。每个行为记录包含三个要素：

$$B = \{(i_1, a_1, t_1), (i_2, a_2, t_2), ..., (i_T, a_T, t_T)\}$$

其中 $i_T$ 表示在时间戳 $T$ 交互的物品，$a_T \in \{click, cart, favorite, purchase\}$ 表示行为类型，$t_T$ 表示行为时间。

该模块的职责是维护一个滑动窗口内的用户行为序列，为后续的意图分析提供数据基础。

#### 3.2.2 Prompt 构建模块

Prompt 构建模块采用自适应策略，根据用户行为特征动态调整 Prompt 的模板和结构。算法流程如下：

**Stage 1: 特征提取**
从行为序列中提取四维特征向量 $\Phi(B) = [\Phi_{act}, \Phi_{rec}, \Phi_{div}, \Phi_{freq}]$：
- $\Phi_{act}$：行为类型分布
- $\Phi_{rec}$：时间衰减权重（近期行为更重要）
- $\Phi_{div}$：语义多样性
- $\Phi_{freq}$：行为频率

**Stage 2: 模板级适配**
从模板池 $T_s$ 中选择最适合当前场景的 Prompt 模板，使用轻量级评分模型 $M_{score}$ 进行评估：

$$p_k = \frac{\exp(\beta \alpha_k)}{\sum_j \exp(\beta \alpha_j)}$$

其中 $\alpha_k$ 是模板 $T_k$ 的评分，最终选择概率最高的模板。

**Stage 3: 结构级适配**
在选定模板的基础上，逐个评估候选结构组件的边际增益 $\Delta(c)$，只有当增益为正且满足资源约束时才将其加入 Prompt：

$$\Delta(c) = M_{score}(P \oplus c, \Phi, s) - M_{score}(P, \Phi, s)$$

**Stage 4: 预算执行与最终化**
执行预算感知的剪枝步骤，确保最终 Prompt 在延迟、内存和 Token 数量约束下最大化效用。

#### 3.2.3 Intent Agent

Intent Agent 是 RecGPT-Mobile 的核心组件，其任务是将复杂的用户行为信号转化为清晰的用户意图查询。输入为自适应构建的 Prompt，输出为预测的下一搜索查询。

**问题形式化**：
给定观察到的行为序列 $B$，任务是预测下一潜在搜索查询 $q \in Q$，其中 $Q$ 是搜索查询空间。目标函数为：

$$q^* = \arg\max_{q \in Q} P(q|B) \quad \text{s.t. Resource Constraints}$$

其中 $P(q|B)$ 表示给定用户最近行为条件下搜索查询的条件概率。

**训练数据构建**：
论文构建了四类训练样本（表1），各占不同比例：

| 样本类型 | 数据来源 | 比例 |
|---------|---------|------|
| 行为驱动样本 | 购买日志和搜索日志 | 60% |
| 共购买关系样本 | 物品级共购买矩阵 | 20% |
| LLM 增强样本 | GPT 重写 | 15% |
| 人工标注样本 | 人工审核数据 | 5% |

#### 3.2.4 意图漂移检测机制

Intent Agent 的核心设计目标是在用户意图变化时更新语义表示，同时在用户行为稳定时避免频繁计算。为此，论文设计了意图漂移检测机制，通过三个互补维度量化意图变化：

**（1）熵变化（Entropy Change）**

用户意图的不确定性通过熵来衡量：

$$H(P_B) = -\sum_k P_B(k) \log P_B(k)$$

绝对熵差定义为：

$$\Delta H = |H(P_B^{(t)}) - H(P_B^{(t-1)})|$$

熵差捕获了用户意图是否变得更加聚焦或更加探索性。当熵增加时，表明用户兴趣变得分散；当熵减少时，表明用户意图更加明确。

**（2）Jaccard 相似度（Semantic Overlap）**

评估连续行为窗口之间的语义重叠：

$$J_A(Z^{(t)}, Z^{(t-1)}) = \frac{|Z^{(t)} \cap Z^{(t-1)}|}{|Z^{(t)} \cup Z^{(t-1)}|}$$

其中 $Z^{(t)}$ 表示当前窗口观察到的标签集合。较低的 Jaccard 分数表示语义焦点发生了较大转移。

**（3）Jensen-Shannon 散度（Distributional Drift）**

显式建模分布漂移：

$$JS(P_B^{(t)}, P_B^{(t-1)}) = \frac{1}{2} KL(P_B^{(t)} \| M) + \frac{1}{2} KL(P_B^{(t-1)} \| M)$$

其中 $M = \frac{1}{2}(P_B^{(t)} + P_B^{(t-1)})$ 是两个分布的平均值。JS 散度是对称的，取值范围为 [0, 1]，更适合用于融合。

**（4）融合漂移评分**

将上述三个信号融合为单一意图漂移评分：

$$\Delta_{intent} = \lambda_1 \cdot \Delta H + \lambda_2 \cdot (1 - J_A(Z^{(t)}, Z^{(t-1)})) + \lambda_3 \cdot JS(P_B^{(t)}, P_B^{(t-1)})$$

其中 $\lambda_1, \lambda_2, \lambda_3 \geq 0$ 且 $\lambda_1 + \lambda_2 + \lambda_3 = 1$ 控制不确定性变化、语义重叠和分布漂移的相对重要性。

**触发条件**：当且仅当 $\Delta_{intent} > \tau$ 时（其中 $\tau$ 是预定义阈值），才触发 LLM 更新 Prompt 并生成新预测。

### 3.3 训练策略与优化

#### 3.3.1 监督微调（SFT）

论文采用 LoRA（Low-Rank Adaptation）技术对预训练 LLM 进行轻量级微调。LoRA 的核心思想是在冻结原模型参数的同时，引入低秩可训练矩阵来捕获任务特定的知识。

实验结果表明，LoRA 微调在所有评估维度上都取得了最高分数，表明轻量级微调的有效性。

#### 3.3.2 模型量化

论文采用 INT8 量化技术来进一步减少模型体积和推理延迟。实验显示，量化后的 LoRA 模型（LoRA+Quant）相比全精度模型只有边际的质量损失，证明了在资源受限部署场景下的鲁棒性。

### 3.4 推理/部署策略

#### 3.4.1 移动端模型选择

考虑到存储限制，RecGPT-Mobile 选择 Qwen3-0.6B-Quant（量化版）作为移动端部署模型。这是一个参数量为 0.6B 的小型 LLM，经过 INT8 量化后可以在移动设备上高效运行。

#### 3.4.2 关键超参数设置

论文通过实验启发式搜索确定了以下超参数：
- $\lambda_1 = 0.4$（熵变化权重）
- $\lambda_2 = 0.3$（Jaccard 权重）
- $\lambda_3 = 0.3$（JS 散度权重）
- $\tau = 0.8$（触发阈值）

#### 3.4.3 延迟分析

论文给出了在真实移动设备上的推理延迟分布（百分位数分析）。虽然较高百分位数显示出增加的延迟，但整体时间趋势在 P50 到 P95 之间保持一致。这表明模型在各种尾部延迟条件下都能保持稳定的执行行为。此外，不同百分位数曲线之间的适度差异反映了真实世界客户端环境中常见的设备级差异，而非系统性性能退化。

## 4. 实验设计与结果分析

### 4.1 实验设置

#### 数据集

论文的实验分为离线评估和在线 A/B 测试两部分：

1. **离线评估数据**：基于淘宝真实用户行为日志构建的内部数据集
2. **在线 A/B 测试**：在淘宝移动端四个 feed 场景进行，历时一个月，覆盖数百万真实用户

#### 评估指标

论文设计了 LLM 驱动的多维评估体系，从三个互补维度评估生成质量：

- **语义一致性（$S_{sem}$）**：生成的查询是否与行为序列隐含的潜在意图语义对齐
- **逻辑连贯性（$S_{logic}$）**：查询是否反映了合理的行为序列意图转换
- **表达质量（$S_{style}$）**：查询是否避免了模板复用，以自然方式表达

最终得分是三个子分数的加权聚合，提供生成质量的整体评估。

#### Baseline 方法

论文比较了以下几种设置：
1. **Base**：未经微调的原始 Qwen3 模型
2. **LoRA**：经过 LoRA 微调的 Qwen3 模型
3. **LoRA+Quant**：经过 LoRA 微调和 INT8 量化的 Qwen3 模型

### 4.2 主实验结果

#### 离线自动评估结果

| 评估模型 | 设置 | $S_{sem}$ | $S_{logic}$ | $S_{style}$ | Total |
|---------|------|----------|------------|------------|-------|
| Qwen3-4B | Base | 0.752 | 0.621 | 0.657 | 0.677 |
| Qwen3-4B | LoRA | 0.885 | 0.792 | 0.811 | 0.829 |
| Qwen3-4B | LoRA+Quant | 0.844 | 0.754 | 0.785 | 0.794 |
| Qwen3-8B | Base | 0.657 | 0.554 | 0.627 | 0.613 |
| Qwen3-8B | LoRA | 0.807 | 0.755 | 0.786 | 0.783 |
| Qwen3-8B | LoRA+Quant | 0.780 | 0.746 | 0.754 | 0.760 |
| Qwen3-30B | Base | 0.671 | 0.654 | 0.663 | 0.654 |
| Qwen3-30B | LoRA | 0.839 | 0.797 | 0.787 | 0.808 |
| Qwen3-30B | LoRA+Quant | 0.812 | 0.774 | 0.762 | 0.780 |

**结果分析**：

1. **LoRA 微调效果显著**：在所有模型规模下，LoRA 微调相比 Base 模型都有大幅提升。例如 Qwen3-4B 的 Total 分数从 0.677 提升到 0.829，提升幅度达 22.5%。

2. **量化代价可控**：LoRA+Quant 相比 LoRA 全精度模型，虽然有一定质量损失，但总体可控。Qwen3-4B 的 Total 分数从 0.829 下降到 0.794，损失约 4.2%，这在移动端部署场景下是可以接受的。

### 方法局限

1. **模型能力的固有限制**：尽管采用了多种优化技术，0.6B 规模的 LLM 在复杂语义理解方面仍然存在局限。对于需要深度推理的意图理解任务，更大规模模型的潜力尚未完全释放。

1. **离线评估的局限性**：自动评估指标（$S_{sem}$、$S_{logic}$、$S_{style}$）是由 LLM 驱动的，可能存在 LLM 评估偏差。

### 工业落地挑战

1. **跨设备兼容性**：不同移动设备的硬件能力差异巨大，需要设计自适应的推理策略来平衡效果和性能。

2. **模型更新与同步**：当 LLM 更新时，如何高效地将新模型推送到数亿台设备是一个巨大的工程挑战。
